# TwinSpace Idempotency System Guide

## Overview

### What is Idempotency?
An **idempotent operation** can be executed multiple times without changing the result beyond the initial execution. In web applications, network dropouts, browser refreshes, double-clicks, and mobile timeouts can trigger duplicate requests.

The TwinSpace Idempotency System guarantees that sending the same write request multiple times returns the original response and avoids duplicate database records, payment double-charges, or redundant emails.

## Architecture & Data Flow

```mermaid
sequenceDiagram
    autonumber
    actor Client as Frontend / Client
    participant Server as Serverless API (/api/*)
    participant Store as Firestore (idempotency_keys)
    participant DB as Backend Services / DB

    Client->>Server: POST with Idempotency-Key: <UUID>
    Server->>Store: Atomic check / reserve (status: PROCESSING)
    alt Already COMPLETED with identical payload
        Store-->>Server: Return cached response
        Server-->>Client: HTTP 200/201 (Idempotent-Replayed: true)
    alt Same Key with DIFFERENT payload
        Server-->>Client: HTTP 409 Conflict
    alt Currently PROCESSING (<60s)
        Server-->>Client: HTTP 409 (Retry-After: 2)
    alt New or Recovered Lock
        Server->>DB: Execute real business logic
        DB-->>Server: Operation succeeded
        Server->>Store: Update record (status: COMPLETED, cached response)
        Server-->>Client: HTTP 200/201 Original Response
    end
```

## Frontend Integration

### Generating and Using Keys
Frontend applications use the helper in `src/lib/idempotency.ts`:

```typescript
import { fetchWithIdempotency, generateIdempotencyKey } from '@/lib/idempotency'

// Option 1: Automatic UUID generation and network retry handling
const { response, data, replayed } = await fetchWithIdempotency('/api/contact', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name, email, message }),
  maxRetries: 2, // Retries automatically using the SAME key
})

// Option 2: Explicit key lifecycle (e.g. multi-step forms)
const key = generateIdempotencyKey() // Cryptographically secure UUIDv4
const res = await fetch('/api/payments/create', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Idempotency-Key': key,
  },
  body: JSON.stringify(paymentDetails),
})
```

> [!IMPORTANT]
> **Retry Rule**: When retrying a failed or timed-out request, **always reuse the original `Idempotency-Key`**. Generating a new key on every retry defeats idempotency. Only generate a new key when the user begins a brand-new submission.

## Firestore Schema

Idempotency records are stored in the `/idempotency_keys` collection:

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `string` | Deterministic SHA-256 hash of `scope::method::endpoint::key` |
| `key` | `string` | The raw client idempotency key (16–255 chars) |
| `scope` | `string` | `user:<userId>` for authenticated users, or `anon:<clientIp>` for public endpoints |
| `endpoint` | `string` | Target API path (e.g. `/api/payments/create`) |
| `method` | `string` | HTTP method (e.g. `POST`) |
| `requestHash` | `string` | SHA-256 of canonicalized request body |
| `status` | `string` | `PROCESSING` \| `COMPLETED` \| `FAILED` |
| `responseStatus`| `number` | HTTP status code returned (e.g. `200`, `201`) |
| `responseHeaders`| `string` | JSON string of cached headers |
| `responseBody` | `string` | JSON string of the returned response |
| `createdAt` | `string` | ISO timestamp of reservation |
| `updatedAt` | `string` | ISO timestamp of last update |
| `completedAt` | `string` | ISO timestamp when operation finished |
| `expiresAt` | `string` | ISO timestamp when record expires (TTL) |

### Security Rules
Client SDKs are completely blocked from accessing `/idempotency_keys`. Access is granted exclusively to trusted serverless functions:

```firestore
match /idempotency_keys/{id} {
  allow read, write: if false;
}
```

## Crash Recovery & Failure Handling

1. **Stale Lock Recovery**: If an operation crashes or times out while `status == 'PROCESSING'`, any request arriving after `processingTimeoutSeconds` (default: 60s) safely reclaims the lock and executes the operation.
2. **Failed Operations**: If an operation fails with a 5xx error or exception, the key is updated to `FAILED`, allowing legitimate retries to re-execute without being blocked.
3. **Payload Mismatch Detection**: Reusing an existing key with a different request body immediately returns `HTTP 409 Conflict` to prevent cross-request collisions.
4. **TTL / Expiration**: Records automatically expire after `ttlSeconds` (default 24h, financial 48h). Expired records are treated as new requests.

## Adding Idempotency to a New Server Endpoint

Wrap your endpoint logic with `handleWithIdempotency`:

```typescript
import { handleWithIdempotency } from './_lib/idempotency'

export default async function handler(req: any, res: any) {
  if (req.method !== 'POST') {
    res.setHeader('Allow', 'POST')
    return res.status(405).json({ error: 'Method Not Allowed' })
  }

  return handleWithIdempotency(
    req,
    res,
    {
      endpoint: '/api/your-feature',
      required: true, // Set to true if Idempotency-Key is mandatory
      ttlSeconds: 24 * 60 * 60,
      getUserId: (r) => r.user?.uid, // Optional user scope
    },
    async () => {
      // Your business logic here:
      const result = await doImportantWork(req.body)

      return {
        status: 200,
        body: { success: true, data: result },
      }
    }
  )
}
```
